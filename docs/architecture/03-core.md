# Ядро: touchbar-core

Ядро содержит всё поведение Touch Bar, которое нужно проверять: маршрутизацию касаний, захваты, жесты виджетов, панели, слои, видимость экземпляров, выбор профиля, политику действий и подписок.

В ядре нет ввода-вывода, wasm, GL, системного времени и случайности. Это детерминированный автомат:

```rust
impl Core {
    pub fn new(config: CoreConfig) -> Self;
    pub fn handle(&mut self, now: Timestamp, input: Input) -> Vec<Output>;
    pub fn snapshot(&self) -> CoreSnapshot; // для status, explain и тестов
}
```

`now` приходит параметром: `Timestamp` — монотонное время в миллисекундах от старта сессии, сериализуемое, в отличие от `Instant`. Ядро не читает часы само, поэтому одна и та же последовательность входов всегда даёт одинаковые выходы. Во всех коллекциях, где важен порядок, используются `BTreeMap` или `IndexMap`, `HashMap` — нигде.

## Вход

| `Input` | Откуда |
|---|---|
| `SurfaceAdded(SurfaceInfo)`, `SurfaceChanged`, `SurfaceRemoved` | `touchbard` или другая поверхность ([16-surfaces.md](16-surfaces.md)) |
| `Touch{surface, contact, phase, x, y}` | поверхность |
| `Key{source, code, phase}` | поверхность (отслеживаемые клавиши `touchbard`) или бэкенд рабочего стола |
| `Mode{surface, display\|native}`, `Revoked{surface}` | `touchbard` |
| `Layout{surface, generation, hit_map, representations, scrubbers, slots, presentation}` | рендер: карта попаданий (прямоугольники виджетов в пикселях) и выбранные варианты `responsive` в ответ на `Render` |
| `Fact{name, value \| absent}` | бэкенд рабочего стола, `touchbar-apps`, модули media и audio |
| `Locale(String)` | оболочка: локаль сессии, до первого сообщения `C`; ядро не читает окружение (D56) |
| `DesktopCapabilities{key}` | оболочка: доступность ввода клавиш из `BackendReady` рабочего стола; при потере возможности ядро отпускает удерживаемые клавиши этого маршрута |
| `Catalog(PluginCatalog)` | загрузчик плагинов: наборы, профили, категории, привязки, уже проверенные |
| `LogicDescribed{instance, description, persisted}` | runtime, после загрузки модуля и чтения сохранённых полей по ключу (D55) |
| `LogicUpdate{instance, call, update}` | runtime: ответ логики на вызов |
| `LogicFault{instance, call, reason}` | runtime: trap, превышение времени, нарушение бюджета |
| `LogicError{instance, call, message}` | runtime: обычный `Err` вызова (D45) |
| `InstanceFault{instance, reason}` | runtime: ошибка загрузки или `describe` до появления `CallId` (D45) |
| `EffectDone{request, result}` | исполнитель действий |
| `SubscriptionData{subscription, data}`, `SubscriptionLost{subscription, error}` | исполнитель подписок |
| `Timer{id}` | оболочка, по `Output::SetTimer` |
| `FrameDone{surface, generation}` | рендер: кадр отправлен, можно планировать следующий; устаревший ответ не открывает слот кадра |

## Выход

| `Output` | Кому |
|---|---|
| `CallLogic{instance, call, invocation}` | runtime: `LogicCall::Init { config, persisted }` или `LogicCall::Handle(LogicEvent)`, с общим `CallId` |
| `CreateInstance{instance, surface, plugin, set, persist_key}`, `DisposeInstance{instance}` | runtime. Создание загружает экземпляр и возвращает `LogicDescribed`, но не запускает `init`. У каждой поверхности свои экземпляры |
| `StartEffect{request, effect, policy}`, `CancelEffect{request}` | исполнитель |
| `Subscribe{subscription, kind}`, `Unsubscribe{subscription}` | исполнитель |
| `SendKey{surface, key, phase}`, `WatchKeys{surface, set}`, `Backlight{surface, limit}` | поверхность, если это есть в её `caps` |
| `DesktopKey{surface, key, phase}` | исполнитель ввода рабочего стола: маршрут клавиш при отсутствии `inject_keys` поверхности и наличии `key` у бэкенда. Если оба маршрута недоступны, запрос получает `unsupported` |
| `Render{surface, generation, scene}` | рендер: дерево сцены и изменённые экземпляры |
| `Persist{instance, key, fields}` | хранилище состояния; ключ остаётся действительным после уничтожения экземпляра |
| `SetTimer{id, at}`, `ClearTimer{id}` | оболочка |
| `CaptureFinished{capture, completion}` | диагностика: исходный CaptureSnapshot (id, поверхность, контакт, цель), завершение Up либо Cancel(reason). Исполнители игнорируют; журнал сохраняет для проверки маршрутизации |
| `Log{level, event}` | журнал и бортовой журнал |

## Модель данных

- **Каталог:** проверенные плагины, наборы, профили, категории, привязки. Заменяется целиком при перезагрузке.
- **Факты:** `BTreeMap<FactName, FactValue>`.
- **Поверхности:** описание каждой поверхности и её сцена. У каждой поверхности свои профиль, стек слоёв, панель и размещённые в них экземпляры, а также последняя карта попаданий. Выбор профиля для поверхности видит общие факты и факты `surface.*` этой поверхности. В v1 реально подключается только Touch Bar, но ядро с самого начала поддерживает несколько поверхностей одновременно ([16-surfaces.md](16-surfaces.md)).
- **Экземпляры:** состояние логики (последний `state`), видимость, запросы и подписки в работе.
- **Диагностический снимок:** содержит активные захваты и `key_leases` с владельцем (контакт, логика или запрос), поверхностью, клавишей и маршрутом surface/desktop. Это проекция уже существующего состояния; формат контрольной точки не меняется.
- **Касания:** таблица захватов `(SurfaceId, ContactId) → Capture`.
- **Привязки:** автомат на каждую привязку сессии (см. [09-bindings.md](09-bindings.md)).

Поколения рендера уникальны в пределах ядра, в том числе после повторного подключения того же `SurfaceId`. На поверхности одновременно ожидается не больше одного кадра; изменения до `FrameDone` объединяются в следующий кадр. Поверхность с `caps.modes` начинает в `native` и ждёт подтверждения `display`; поверхность без переключения режимов всегда в `display`.

## Автоматы

### Экземпляр

```
            CreateInstance
 ┌────────┐ ─────────────▶ ┌─────────┐  LogicDescribed + init   ┌────────┐
 │ (нет)  │                │ Loading │ ───────────────────────▶ │ Hidden │ ◀─┐
 └────────┘                └─────────┘                          └────────┘   │
                                ▲                         показ  │   ▲ скрытие│
                     backoff    │                                ▼   │       │
                           ┌─────────┐   trap / таймаут    ┌─────────┐       │
                           │ Faulted │ ◀────────────────── │ Visible │ ──────┘
                           └─────────┘    (из любого)      └─────────┘
                                │ профиль больше не содержит экземпляр
                                ▼
                           ┌──────────┐
                           │ Disposed │  (терминальное, из любого состояния)
                           └──────────┘
```

| Переход | Что делает ядро |
|---|---|
| → `Hidden` (после `init`) | Применяет `state` из `init`. Подписки **без** `background` не запускаются |
| `Hidden` → `Visible` | `CallLogic(shown)`, запуск подписок экземпляра, рендер |
| `Visible` → `Hidden` | Отмена касаний экземпляра (`Cancel{Hidden}`), отмена действий с `until-hidden`, остановка подписок без `background`, затем `CallLogic(hidden)` |
| → `Faulted` | Отмена касаний (`Cancel{Fault}`), всех подписок и действий `until-hidden`. Элемент показывает заглушку. Повтор через 1, 2, 4… 60 с |
| → `Disposed` | Как `Hidden`, плюс `DisposeInstance`. Действия `committed`, и выполняющиеся, и ожидающие очереди, всё равно доводятся до конца, но их результат отбрасывается |

Экземпляр под слоем (например, когда по Fn показаны F-клавиши) остаётся `Visible`: он не получает касаний и не рисуется, но подписки работают. Логика об этом не узнаёт, а при снятии слоя картинка появляется мгновенно.

После `LogicDescribed` ядро проверяет описание и выдаёт `CallLogic(Init { config, persisted })`. Ответ приходит как обычный `LogicUpdate { instance, call, update }`: только успешный ответ на текущий `Init` переводит экземпляр из `Loading` в `Hidden`, после чего возможен показ. `Init` занимает тот же единственный слот вызова, что и `Handle`; обычные события в `Loading` не отправляются. `LogicCall` — тип хоста, а не дополнительный вариант события WIT (D41).

При скрытии обычные Action-вызовы в очереди удаляются, а уже поставленные
`Cancelled` сохраняются перед `Hidden`. Если слот вызова занят, cleanup приходит
после его завершения, даже при текущем статусе `Hidden`. Это исключение I5
относится к живому экземпляру того же поколения; новых действий оно не разрешает.
Отмена захватов, отпускание клавиш и остановка foreground-подписок происходят
сразу. `DisposeInstance` не ждёт обработки очереди, уничтоженному экземпляру
cleanup не доставляется (D59).

`LogicError` завершает текущий вызов. Для `Handle` состояние сохраняется и очередь продолжается; для `Init` экземпляр переходит в `Faulted` с backoff (D45). `InstanceFault` применяется только к загрузке до успешного `LogicDescribed`. Ошибка схемы набора не повторяется по таймеру: повтор разрешает новая успешная загрузка каталога. Повтор после сбоя увеличивает поколение экземпляра; ответы и таймеры прежнего поколения игнорируются. Успешный обычный `Handle` сбрасывает backoff.

`SceneItem.status` позволяет рендеру отличить загрузку, готовый экземпляр и заглушку после сбоя. Состояние и очередь каждого экземпляра отражаются в `CoreSnapshot`; уничтоженные экземпляры из него удаляются.

### Касание

```
Down ──hit-test──▶ Captured(target, widget) ──Move*──▶ ... ──▶ Up
                                                         └──▶ Cancel(reason)
```

- **Цель.** Для `Down` цель определяется по последней карте попаданий поверхности (`Layout`): панель, затем слой, затем профиль. Если касание не попало ни в один виджет, срабатывает запасной вариант из исходного проекта: ближайший виджет в той же колонке, не дальше порога по вертикали. Пороги жестов заданы в миллиметрах и переводятся в пиксели через `px_per_mm` поверхности ([16-surfaces.md](16-surfaces.md)).
- **Устаревшая карта.** Пока рендер не ответил на новый `Render`, используется предыдущая карта. Если касание попало в экземпляр, которого в новой сцене нет, оно отменяется с причиной `Layout`.
- **Причины отмены:** `Hidden`, `Layer`, `Presentation`, `Profile`, `Layout`, `Mode`, `Revoked`, `Fault`, `Hardware` (cancel от поверхности), `SurfaceRemoved`.
- **Завершение.** `Up` и `Cancel` доставляются по таблице захватов, а не по текущей сцене.

### Виджет

Жесты разбирает ядро, а логика получает только их смысл.

| Виджет | Автомат | События для логики |
|---|---|---|
| `button` | `Idle → Pressed → (Held)` | `pressed`, `long-pressed` (после `hold-ms`), `activated` (Up внутри, если не было long-press или он не задан), `released`, `cancelled` |
| `slider` | `Idle → Dragging` | `pressed`, `value-changed` (не чаще одного раза за кадр), `activated` (Up), `cancelled` |
| `scrubber` | `Idle → Scrolling → Selecting` | `value-changed`, `selected` |
| `key` | `Idle → Down` | Логика не участвует: `Down` даёт `SendKey(pressed)`, а `Up` и `Cancel` дают `SendKey(released)` |

Состояние взаимодействия хранится в ядре отдельно от `StatePatch` плагина и возвращается рендеру в `SceneItem.interactions`: нажатие, значение ползунка, смещение scrubber в пикселях, подсветка и выбранный `record_key` (D47).

Для scrubber вход `Layout.scrubbers` содержит `instance`, `widget`, прямоугольник области в пикселях поверхности, полную ширину содержимого и прямоугольники элементов с уникальными `record_key`. Геометрия элементов задаётся относительно начала содержимого, без смещения и обрезки. Прокрутка свободная, выбор происходит при отпускании; `value-changed` передаёт смещение в базовых единицах набора, `selected` — `record_key` без числового индекса. Отмена восстанавливает состояние до жеста. Изменение геометрии во время жеста отменяет его с `Layout`.

Ползунок объединяет движения между подтверждениями кадров; при `Up` последнее значение доставляется перед `activated`, даже если следующий кадр ещё не подтверждён. Одним ползунком или scrubber в каждый момент управляет одно касание. Кнопки и клавиши допускают несколько касаний с независимым завершением.

У каждого события логики есть поле `origin`: `physical` (вызвано пальцем) или `synthetic` (отмена, вызванная ядром).

### Панель (presentation)

| Состояние | Событие | Переход |
|---|---|---|
| `Closed` | логика вернула `presentation.open` в ответ на **`physical`** событие | `Open(owner, panel, anchor)` |
| `Closed` | `presentation.open` в ответ на `synthetic` | игнорируется, `Log{warn}` |
| `Open` | `Down` вне панели и политика `outside-press` | `Closed`, `Cancel{Presentation}` для касаний внутри панели |
| `Open` | `activated` в панели и `dismiss-on-selection` | `Closed` после ответа на обработчик (в том числе `Err`); без обработчика — сразу |
| `Open` | `transient`, касание-якорь завершено | `Closed` |
| `Open` | смена профиля или слоя, Fn, режим `native`, владелец скрыт или упал | `Closed` |

На каждой поверхности в каждый момент открыта не больше одной панели, поверхности независимы (I12). Пока панель открыта, новые `Down` идут в неё, а касания, начатые до её открытия, остаются у своих целей до завершения. Б2 из исходного проекта так невозможен по построению. Виджеты панели используют экземпляр, логику и состояние набора-владельца; открытие и закрытие не создают wasm-экземпляр и не переводят владельца в `Hidden` (D48).

Для физического вызова хост сохраняет исходный `CaptureId`, цель, поверхность и прямоугольник якоря в приватных данных очереди и выполняющегося вызова. Эти данные не входят в WIT. `transient` открывается только пока жив именно этот захват; повторное использование `ContactId` его не оживляет. `persistent` может открыться после `Up`, сохранив исходный якорь. После `Cancel` разрешение на открытие отзывается у очередных и выполняющихся вызовов этого захвата; сам `Cancelled` также не разрешает открытие. Контекст другого касания сохраняется. Это не отменяет уже принятых committed-действий (D60). Ответ от уже закрытой или заменённой панели не открывает другую (D49).

`Layout.slots` содержит границы слотов по `InstanceId`, включая пустое место. `Scene.presentation` передаёт ID панели, владельца, описание, размещение, lifetime, якорь и область. Для `region` область — слот владельца, для `full` — поверхность, для `anchored` рендер использует исходный прямоугольник виджета и слот владельца. Рендер рассчитывает окончательное размещение и возвращает `Layout.presentation { id, bounds }` (D50). До получения геометрии панели новые касания не принимаются. Чужой ID панели или некорректные границы отвергают раскладку целиком; запоздалые раскладки закрытой панели игнорируются.

Нажатие вне панели поглощается: при `outside-press` закрывает её, иначе оставляет открытой. `release` относится только к исходному касанию-якорю и панели, открытой до его Up: отпускание, открывшее новую persistent-панель, её не закрывает; `transient` закрывается при его завершении независимо от этой политики. `timeout` отсчитывается от открытия. Выбор закрывает исходную панель, но не новую панель, открытую ответом того же обработчика. Закрытие отменяет касания панели, отпускает её клавиши и ставит `presentation-closed` в очередь владельца. Изменение поверхности закрывает панель и инвалидирует геометрию слотов. Касания под панелью сохраняют свои цели и после её закрытия, пока рендер не вернул раскладку основной сцены.

Встроенный `expanded_panel` открывает `persistent` при активации; `press_and_hold_panel` открывает `transient` при достижении заданного `hold_ms`. Оба используют `anchored` и работают без wasm.

### Слои

Стек слоёв над профилем управляется привязками: `layer`, `toggle-layer` и `clear-layers`. На поверхности одна копия слоя на набор, с независимыми удержаниями и постоянным флагом (D51). Правила источников и сброса — в [09-bindings.md](09-bindings.md).

`Scene.items` содержит экземпляры профиля и всех слоёв. `ScenePlane::Layer(n)` задаёт текущую позицию в стеке (1 — нижний слой); верхний слой рисуется и принимает новые касания, включая запрет попаданий через пустые места в профиль. Экземпляры под ним остаются `Visible`. Позиция не входит в идентичность экземпляра: перемещение сохраняет логику и состояние, а слой и слот профиля имеют разные идентичности даже для одного набора. Новое поколение содержимого пересоздаёт экземпляр по D44.

При изменении верхнего слоя касания отменяются с причиной `Layer`, панель закрывается. При снятии нижнего слоя захват верхнего сохраняет исходный виджет и прямоугольник, даже если позиция в стеке изменилась. Запоздалые раскладки прежнего стека игнорируются; ответы логики из закрытой панели или покрытого профиля не открывают панели поверх нового слоя.

### Профиль

| Состояние | Событие | Переход |
|---|---|---|
| `Active(p)` | факты или каталог дали другой профиль `q` | если нет активных захватов и незавершённых физических Action-вызовов — сразу `Active(q)`, иначе `Pending(p, q, deadline = now + 1500 мс)` |
| `Pending(p, q)` | последний захват и последний физический Action-вызов завершились | `Active(q)` |
| `Pending(p, q)` | наступил `deadline` | `Cancel{Profile}` для всех захватов, отбрасывание незавершённых вызовов, `Active(q)` |
| `Pending(p, q)` | факты снова дали `p` | `Active(p)` |
| `Pending(p, q)` | факты дали `r` | `Pending(p, r)` с прежним `deadline` |

Ожидание включает физические Action-вызовы в очереди и в исполнении: иначе `Activated`, поставленный в очередь при последнем `Up`, мог бы потеряться до принятия его эффекта. Исходный deadline не продлевается. По deadline физические вызовы в очереди удаляются, кроме уже поставленных Cancelled. Для уже завершённых касаний с отброшенной работой ставится один синтетический Cancelled(Profile), если задан обработчик; старые Released/Activated не выполняются (D61); ответ уже выполняющегося вызова игнорируется, включая сохранённый между профилями экземпляр. Его слот остаётся занятым до завершения: второй вызов параллельно не запускается. Уже принятые `committed`-запросы переживают принудительное переключение по D37 (D46). Истечение Pending через обновление фактов или каталога и через Timer проходит один переход ядра: сначала отмена захватов и отбрасывание старой физической работы, затем переключение профиля. Сам автомат ProfileSwitch только обновляет Pending; его expire вызывается ядром после cleanup.

При смене профиля экземпляры, которые есть в обоих профилях (тот же плагин, набор и `logic_config` в слоте с тем же id), сохраняются. Остальные проходят через `Hidden` и `Disposed`, а новые — через `Loading`. Алгоритм выбора профиля — в [08-profiles.md](08-profiles.md).

При замене каталога дополнительно сравниваются ревизия владельца набора и идентификатор с ревизией поставщика логики (D44). Изменение любого из них пересоздаёт экземпляр, сохраняя сохраняемые поля. Повторное чтение того же содержимого и изменение только плагина профиля не пересоздают прежние наборы. Изменение единиц профиля обновляет сцену без сброса экземпляра.

### Действия и подписки

| Состояние | Событие | Переход |
|---|---|---|
| — | логика вернула допустимый запрос | `Requested`. Если у ключа `coalesce` уже есть запрос в работе, новый заменяет ожидающий, но не выполняющийся |
| `Requested` | у экземпляра есть свободный слот (по умолчанию 8 одновременно) | `Running`, `StartEffect` |
| `Running` | `EffectDone` | экземпляр жив — `CallLogic(effect-done)`, иначе результат отбрасывается |
| `Running` | экземпляр скрыт и `lifetime = until-hidden` | `CancelEffect`, логика получит `effect-done(cancelled)`, если экземпляр не уничтожен |
| `Requested` или `Running` | логика вернула `cancel` с тегом запроса | `CancelEffect` (для `Running` — с прерыванием, насколько его поддерживает исполнитель), `effect-done(cancelled)`. Относится к любому `lifetime` |
| `Running` | истёк `timeout` | `CancelEffect`, `effect-done(timeout)` |

Новые until-hidden от Hidden отклоняются с предупреждением без EffectDone (D62); уже принятые при Visible отменяются с cancelled. Запросы committed хранятся независимо от wasm-экземпляра. Ядро принимает requests/cancel/subscriptions до завершения Pending профиля (D46), затем синхронизирует видимость и допускает выполнение по квотам. Таймаут начинается в Running. Синхронные действия key выполняются самим ядром через учёт владельцев; key.down имеет проверку D53. Таймеры ожидания эффектов и backoff подписок входят в общий реестр.

Подписки — это желаемое множество, которое возвращает логика. Ядро вычисляет разницу с текущим множеством и выдаёт `Subscribe` и `Unsubscribe`. Перезапуск после `SubscriptionLost` идёт с backoff 1, 2, 4… 60 с, логика получает `subscription-lost`.

## Инварианты

Их проверяют property-тесты на случайных последовательностях входов (см. [13-testing.md](13-testing.md)).

1. **I1.** У каждого `Down` ровно одно завершение (`Up` или `Cancel`), и оно доставлено той же цели, что и `Down`.
2. **I2.** После завершения касания его нет в таблице захватов. Если все касания завершены, таблица пуста.
3. **I3.** `Pending` профиля всегда разрешается не позже `deadline`.
4. **I4.** На каждой поверхности открыта не больше одной панели. Панель закрывается, если её владелец перестал быть `Visible`.
5. **I5.** Скрытый экземпляр не получает действий и событий касаний и не держит подписок без `background`. Исключение — уже поставленный до скрытия cleanup `Cancelled`, доставляемый живому экземпляру того же поколения перед `Hidden` (D59).
6. **I6.** Принятое ядром действие `committed` не отменяется из-за изменений интерфейса: скрытия, уничтожения экземпляра, смены профиля, слоя или панели (сценарий A2 исходного проекта). Его отменяют только таймаут, явный `cancel` от логики и замена через `coalesce`: ожидающий запрос заменяется новым с тем же ключом, а выполняющийся не прерывается.
7. **I7.** Результат действия или данные подписки никогда не доставляются экземпляру, который уничтожен или пересоздан.
8. **I8.** Логика не получает событий в `Loading`, `Faulted` и `Disposed`.
9. **I9.** Каждая отправленная клавиша `pressed` получает `released`, даже при отмене касания, скрытии, смене режима или отзыве. Ядро выдаёт завершающие релизы; `touchbard` независимо отпускает введённые клавиши перед native, отзывом и закрытием соединения (D43).
10. **I10.** Сбой одного экземпляра не меняет состояние других, если не считать перераскладки.
11. **I11.** Для поверхности в режиме `native` ядро не выдаёт `Render` и новые `SendKey(pressed)`. Исключение — завершающие `SendKey(released)` при переходе в native или отзыве (D43). Ядро не выдаёт команд, которых нет в `caps` поверхности.
12. **I12.** Поверхности независимы: события одной поверхности не меняют касаний, панелей и слоёв другой, если не считать общих фактов и явно заданных целей привязок `all`/`surfaces` (D52).

## Бортовой журнал

Ядро — чистая функция. Поэтому любую ситуацию воспроизводят **полное состояние ядра на начало отрезка и входы после него**. Одних входов, начальных фактов и хешей каталога для этого мало: ядро к началу буфера уже имеет захваты, экземпляры, очереди, таймеры и состояние логики.

```rust
impl Core {
    pub fn checkpoint(&self) -> CoreState;          // полное сериализуемое состояние
    pub fn restore(state: CoreState) -> Result<Self, RestoreError>;
}
```

- `CoreState` содержит **версию формата**, **`CoreConfig`** (таймауты, пороги, лимиты: с другими значениями те же входы дали бы другие выходы) и всё состояние: каталог целиком (а не хеши), факты, поверхности и сцены, экземпляры с последним `state` логики, очереди вызовов, запросы и подписки, захваты, автоматы привязок и таймеры, счётчики идентификаторов. `CoreSnapshot` для `status` — его урезанное представление: режим, разрешение профиля, слои с владельцами удержаний, панель, экземпляры с состоянием и очередями, запросы, подписки и захваты. Незавершённые committed-запросы остаются видны и после удаления владельца. Контрольная точка также хранит кеш сохраняемых полей и отложенные записи.
- `restore` берёт конфигурацию из самого `CoreState`. Неизвестная версия формата даёт `RestoreError::Version`: дамп чужой версии не воспроизводится молча с другими правилами.
- Инвариант детерминизма: `restore(checkpoint(c))` после тех же входов даёт те же выходы, что и `c`. Его проверяет property-тест.
- Оболочка делает **начальную** контрольную точку сразу после `Core::new`, затем каждые 2000 входов, и хранит две последние вместе со всеми входами после старшей из них. Дамп содержит старшую из хранимых контрольных точек и все входы после неё: до 4000, а пока входов меньше 2000 — начальную точку и все входы с начала сессии ([12-diagnostics.md](12-diagnostics.md)).
