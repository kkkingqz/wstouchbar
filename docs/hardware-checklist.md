# Проверки Touch Bar на стенде

Рабочая ветка: `stage-4-touchbard`. Установка и полный чек-лист появятся в H16–H18.
До завершения H6 не переходить к H7: сначала проверить DRM на настоящем устройстве.

## Рубеж H6: probe

`probe` — самостоятельная диагностика, проектный демон для неё запускать не нужно.
Команда меняет конфигурацию USB Touch Bar и выводит тестовый рисунок. Запуск с root
выполняет пользователь либо агент после явного подтверждения. Обычный `cargo test`
эти операции не выполняет.

1. **До любого переключения USB установить изоляцию от композитора.**
   `packaging/udev/99-wstouchbar-isolation.rules` должен быть установлен с владельцем
   root и правами 0644 в каталоге правил udev. Для временного стенда подходит
   `/run/udev/rules.d` (исчезает при перезагрузке), для установки — `/usr/lib/udev/rules.d`.
   Проверить `udevadm verify FILE` и выполнить `udevadm control --reload`.
   Правило исключает только карту appletbdrm и дигитайзер Touch Bar из seat0;
   обычные GPU и native-клавиатуру оно не затрагивает. `probe` проверяет доверенную
   установленную копию; рабочий поток перечитывает правила до modprobe/USB.

   **Без этого предусловия тест 2026-10-17 спровоцировал ошибки GPU и падение GNOME.**
   Подробности: [протокол](validation/stage-4.md). Успешного выхода probe недостаточно:
   после прогона проверить PID GNOME и отсутствие новых ошибок GPU/GBM/Cogl.

2. Убедиться, что другой процесс не владеет Touch Bar. Если используется tiny-dfr
   или другой аппаратный демон, остановить именно этот процесс/юнит на время проверки.
   Наличие установленного сервиса wstouchbar не предполагается. `probe` отказывается
   работать при занятом `device.lock` или невозможности получить DRM master.
3. Собрать бинарник из рабочего дерева H6:

   ```sh
   cd /home/king/Projects/wstouchbar/.worktrees/stage-4-touchbard
   cargo build --release -p touchbard
   ```

   В текущем контейнере сборки `CARGO_TARGET_DIR=/workspace/target`: на хосте результат —
   `/home/king/Projects/wstouchbar/target/release/touchbard`. Без этой настройки Cargo
   использует `target/release/touchbard` внутри рабочего дерева.
4. На хосте запустить собранный бинарник:

   ```sh
   sudo /home/king/Projects/wstouchbar/target/release/touchbard probe
   ```

   Должны появиться чёрный кадр, тестовая сетка и изменение небольшого участка.
   Затем полоса возвращается в native. JSON-отчёт содержит четыре замера: полный
   и частичный кадры для неблокирующего и блокирующего commit. `actual` показывает
   реально использованный путь: если драйвер отверг NONBLOCK либо не гарантирует
   монотонные метки времени, запасной путь честно помечен `blocking`.
5. Сохранить отчёт и проверить:
   - `prime_cloexec=true`, `native_safe=true`; отдельно `native_hid_ready`;
   - три экспортируемых буфера, XRGB8888, pitch с учётом выравнивания ширины 64;
   - `damage_supported=true`, корректный рисунок после частичного обновления;
   - разумные `commit_us`, без ожидания очереди/IPC/создания damage blob;
   - возврат native после ошибки и после Ctrl+C (SIGINT); SIGTERM/SIGHUP также
     запускают возврат. SIGKILL и отключение питания обработать невозможно.
6. Сравнить физические размеры из `physical_size` с линейкой: длина и высота
   светящейся области в миллиметрах, не корпуса. Передать модель DMI, измерения
   и отчёт. Таблица DMI пока пуста: оценка 6 px/мм явно помечается `fallback`
   с предупреждением и не выдаётся за измерение.

Если возврат в native завершился ошибкой, не продолжать этап и сохранить stderr.
Для ручного восстановления конфигурации USB (только после остановки её владельца):

```sh
sudo sh -c '
for device in /sys/bus/usb/devices/*; do
    [ "$(cat "$device/idVendor" 2>/dev/null)" = 05ac ] || continue
    [ "$(cat "$device/idProduct" 2>/dev/null)" = 8302 ] || continue
    printf "0\n" > "$device/bConfigurationValue" || exit 1
    printf "1\n" > "$device/bConfigurationValue" || exit 1
done
'
```

Это аварийный возврат USB, без изменения параметров autodim: H6 их не перехватывает.
После восстановления проверить появление native HID и клавиш самой полосы.
